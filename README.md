# japanese-study-grammar

일본어 **표현 구조** 학습 메일링. [japanese-study](https://github.com/hexartrion-oss/japanese-study)의
자연스러운 지문 생성 파이프라인을 그대로 가져와, 학습 대상을 표현 구조로 좁힌 자매 리포지토리다.

> 이 리포는 두 차례 전면 개편을 거쳤다. 최초 버전은 동사 활용표를 만드는 방식이었지만
> "사전만 찾으면 풀리는 것"이라는 문제 제기 이후 방향을 완전히 바꿨다. 이후 레벨 표기가
> 실제로 존재하지 않는 급수(`N2+` 등)를 지어내는 문제, 위험한 표현이 문법적으로 잘못
> 쓰이는 문제도 추가로 발견되어 수정했다. 이 문서는 그 모든 개편 이후의 최종 방침만 담고 있다.

## 핵심 원칙

**1. 힌트를 주지 않는다.**
지문에 강조 표시, 문법 설명, 한국어 번역을 일절 넣지 않는다. 학습자가 지문을 읽고 스스로
번역하면서 "이 표현이 왜 여기 있는지"를 알아채는 방식이다. 정답을 주면 그 순간 암기 문제가
되어버린다. Gemini가 임의로 마크다운 강조(`**`)를 넣는 경우가 있어, 프롬프트에서 이를
명시적으로 금지한다.

**2. 카테고리를 숨긴다.**
메일 제목에도, 본문 어디에도 오늘이 무슨 카테고리인지, 무슨 레벨인지 드러나지 않는다.
카테고리 정보는 운영자용 `run_log.txt`에만 남는다. 사용자가 보는 건 순수한 읽을거리
한 편뿐이다. (레벨 배지를 표시했던 적이 있으나, 실제로 존재하지 않는 급수 표기가 되어
전면 제거했다 — 아래 "레벨 표기를 없앤 이유" 참고)

**3. 표현은 단어가 아니라 구조로만 다룬다.**
부사 하나(せっかく)를 그냥 던져놓지 않는다. 반드시 구문 세트(せっかく〜のに)로 등록한다.
빼면 문장이 안 되는 것, 접속 형태가 있는 것만 다룬다.

**4. 표현 뱅크는 스크래핑하지 않는다.**
JLPT 학습 사이트들의 문형 목록은 그 자체가 저작물이다. 개수·분류 체계 같은 규모 감각만
참고하고, 실제 항목은 하나하나 직접 검증해서 채운다. 그래서 카테고리별 개수가 균일하지
않고, 운영하면서 실제 지문에 넣어본 것만 점진적으로 늘어난다.

**5. 같은 표현이 너무 자주 반복되지 않게 한다.**
쿨다운 로직으로 최근 사용 이력을 추적한다. 아래에서 자세히 설명한다.

**6. 결합이 까다로운 표현은 이중으로 검증한다.**
표현 중에는 `にかたくない`(想像에만 붙는다), `ないことには`(뒤에 부정형이 와야 완성된다)처럼
아무 데나 끼워 넣으면 문법이 틀리는 것들이 있다. 이런 표현은 프롬프트에 사용 지침을 붙이고,
생성된 지문에서 실제로 그 지침대로 쓰였는지 구조적으로 재확인한다. 아래 "위험 표현 검증"
참고.

## 요일별 카테고리

| 요일 | 카테고리 | 보유 표현 수 |
|---|---|---|
| 월 | 부사 (부사+구문 세트) | 16 |
| 화 | 인용 (인용·전문·양태) | 17 |
| 수 | 강조·역접 (강조 조사·역접 접속) | 16 |
| 목 | 비즈니스 (비즈니스·뉴스체 논리 접속) | 19 |
| 금 | N1문어체 (N1 문어체 전용) | 21 |

주말은 순환표에 없고, 스크립트가 실행되면 자동으로 월요일 카테고리로 대체된다.

표현 목록 실물은 `grammar_bank.py`에 있다. 예시(부사 카테고리 일부):
`せっかく〜のに · どうせ〜なら · たとえ〜としても · むしろ〜べきだ · いっそ〜ばよかった`

## 레벨 표기를 없앤 이유

처음에는 카테고리마다 `[ N3+ ]`, `[ N2+ ]` 같은 배지를 문서에 달았다. 그런데 이 표기는
두 가지 문제가 있었다.

1. `N2+`, `N3〜N2` 같은 표기는 JLPT에 실제로 존재하지 않는 급수다. 공식 급수는
   N1~N5 다섯 개뿐인데, 편의상 만들어낸 조합 표기를 마치 공식 등급처럼 노출한 셈이었다.
2. 89개 표현을 실제 통용 급수로 재검증해보니, 카테고리 내부에 급수가 넓게 섞여 있어서
   (예: 비즈니스 카테고리 안에 N3부터 N1까지 다 있음) 카테고리 하나에 대표 급수 하나를
   붙이는 방식 자체가 애초에 정확할 수 없었다. 표기를 정직하게 고쳐도(`N3/N2/N1`)
   카테고리 5개 중 4개가 똑같은 표기가 되어버려 정보로서 의미가 없었다.

정확한 급수를 표시하려면 "오늘 실제로 뽑힌 5개 표현의 급수만 모아서 동적으로 표시"하는
방법도 검토했으나, Gemini가 지시받은 급수로 정말 잘 썼는지까지 검증하는 건 신뢰도가
낮고 비용도 크다고 판단해 보류했다. 그래서 현재는 레벨 표기 자체를 문서에서 완전히 뺐다.

## 위험 표현 검증

89개 중 12개는 결합 범위가 좁거나(콜로케이션 제약), 뒷문장과 짝을 이뤄야 완성되는
표현이다. 이런 표현은 `grammar_bank.py`에서 문자열이 아니라 `(표현, 사용지침)` 튜플로
등록되어 있고, 두 단계로 검증한다.

1. **프롬프트 지침**: Gemini에게 "이 표현은 반드시 이런 문맥에서만 써라"를 명시
2. **사후 구조 검증** (그중 10개, `get_grammar.py`의 `_EXTRA_CHECKS`): 프롬프트를
   무시해도 걸러지도록, 지문 생성 후 다시 한번 구조를 확인
   - `ないことには`, `なくしては` — 뒤에 부정형 결론이 있는지
   - `いかんによって` — 뒤에 "달라진다"는 서술이 있는지
   - `あげく`, `ばかりに` — 뒤에 부정적 결과 어휘가 있는지
   - `にかたくない`, `を禁じ得ない` — 앞에 정해진 어휘군(想像·涙 등)이 있는지
   - `きらいがある` — 직전에 `つつある`가 없는지 (이중 완곡화 방지)
   - `そうだ(伝聞)`, `そうだ(様態)` — 직전 활용형을 분석해 실제로 그 형태로 쓰였는지

나머지 4개(`くせに`, `つつも`, `と相まって`, `にたえない`)는 감정 뉘앙스나 다중 요인
판단이 필요해 문자열 패턴만으로 구조 검증이 어려워 프롬프트 지침에만 의존한다. 이 부분은
한계로 남아 있다.

## 문서 템플릿

원본 japanese-study와 같은 형식이다. 차이는 소스 URL 줄이 없다는 것(지어낸 이야기라 출처가
없음)과, 레벨 배지가 없다는 것이다.

```
日本語学習 表現読解
2026-09-07 (Mon) | Week 37

テーマ: 転職を迷う友人の話

（10〜15문장 순수 일본어 지문 — 강조·설명·번역·레벨 표시 전혀 없음）
```

메일 제목도 카테고리를 노출하지 않는 중립적인 형태다: `日本語学習 表現読解 · 2026-09-07 (Mon)`

PDF 파일명은 `JPN_2026-09-07_表現読解.pdf`처럼 날짜가 들어가 매일 파일명이 겹치지 않는다.

## 쿨다운 로직

1. 매일 실행 시 오늘 카테고리에서 **최근 3회** 안에 쓰인 표현을 이력 파일에서 확인한다
2. 그 표현들을 제외한 후보 중에서 5개를 무작위로 뽑는다
3. Gemini로 지문을 생성하고, 5개가 실제로 자연스럽게 들어갔는지(+ 위험 표현은 구조까지)
   검증한다
4. 검증에 실패하면 재시도한다 (2회 실패 시 표현 조합 자체를 교체)
5. 검증을 통과해 **메일 발송에 성공한 경우에만** 이력을 갱신하고 리포지토리에 자동 커밋한다

발송이 실패하면 이력을 건드리지 않는다 — 안 보낸 표현을 "사용됨"으로 잘못 기록하는 걸
막기 위해서다.

카테고리당 16~21개 보유 중이라, 최근 3회를 제외해도 후보가 충분히 남는다. 조합 수 기준으로
1년(52주) 순환에는 여유가 크다. 다만 개별 표현 하나는 카테고리 내에서 평균 3~4주마다
재등장하는데, 이는 의도된 설계다 — 너무 길지도 짧지도 않은 간격 반복이 오히려 기억에 도움이
된다.

이력은 `used_history.json`에 저장되고, GitHub Actions 실행 환경에서는 워크플로가 발송 성공
시 이 파일을 자동으로 커밋·푸시한다. GitHub Actions는 매번 새 가상머신에서 시작하기 때문에,
이 자동 커밋이 없으면 다음 실행이 이전 이력을 전혀 알 수 없다.

## 파일 구성

```
grammar_bank.py   표현 뱅크 (요일별 카테고리, 검증용 파서, 위험 표현 사용지침 포함)
get_grammar.py    카테고리 선정 → 쿨다운 필터링 → 지문 생성 → 검증 → 발송 → 이력 커밋
```

## 설정

리포지토리 Secrets에 다음 4개를 등록한다.

| 이름 | 설명 |
|---|---|
| `GMAIL_ADDRESS` | 발신 Gmail 주소 |
| `GMAIL_APP_PASSWORD` | 2단계 인증 후 발급한 앱 비밀번호 16자리 |
| `EMAIL_RECIPIENTS` | 수신자, 쉼표로 구분 |
| `GEMINI_API_KEY` | Google AI Studio 발급 키 |

로컬 실행은 `.env.example`을 `.env`로 복사해 채운다.

```bash
pip install -r requirements.txt
python get_grammar.py
```

특정 카테고리만 확인하려면 (카테고리 키는 한글):

```bash
FORCE_CATEGORY=N1문어체 python get_grammar.py
```

Actions에서는 **Run workflow**로 카테고리와 수신자를 지정해 수동 실행할 수 있다. 드롭다운은
한글 카테고리명(부사·인용·강조·역접·비즈니스·N1문어체)으로 표시된다. `mail_to`를 채우면 그
주소로만 발송돼서, 다른 구독자에게 테스트 메일이 가는 걸 막을 수 있다.

로컬 실행에서는 이력 파일이 로컬에만 저장되고 git 커밋은 되지 않는다(`GITHUB_ACTIONS` 환경
변수가 있을 때만 커밋을 시도한다).

## 폰트

지문에 일본어만 들어가므로 일본어 전용 폰트로 충분하다. 워크플로는 `fonts-noto-cjk`를
설치한다. 제목을 굵게 표시하기 위해 Bold 폰트(`NotoSansCJK-Bold.ttc`)도 함께 찾는다(없으면
Regular로 대체). 직접 지정하려면 `JAPANESE_FONT_PATH` / `JAPANESE_FONT_PATH_BOLD`를 쓴다.

## 검증 로직의 한계

- 표현이 실제로 지문에 들어갔는지는 부분 문자열 매칭으로 확인한다. 완전한 문법 파싱이
  아니라서, 우연히 같은 글자가 다른 의미로 등장해도 통과 처리될 수 있다 (예: `上で`는
  표현이지만 일반적인 "~위에서"라는 뜻으로 쓰여도 매칭된다).
- Gemini가 한자로 표기하는 흔한 경우(예: `ば良かった` vs `ばよかった`, `想像に難くない` vs
  `想像にかたくない`)는 정규화 테이블로 보정하지만, 모든 한자/히라가나 변형을 다 커버하지는
  못한다.
- `そうだ(伝聞)`와 `そうだ(様態)`는 표기가 똑같이 `そうだ`지만, 직전 활용형(사전형/た형/だ
  → 伝聞, ます형 어간/형용사 어간 → 様態)을 분석해서 구분한다. 동사 활용어미가 항상
  히라가나로 표기되는 관습을 이용한 것이라 정확도가 높지만, 100% 완벽하지는 않다.
- 위험 표현 12개 중 8개만 구조 검증이 있고, 나머지 4개(`くせに`, `つつも`, `と相まって`,
  `にたえない`)는 프롬프트 지침에만 의존한다.
- 표현이 "문법적으로 맞게" 쓰였는지는 어느 정도 검증하지만, 그 표현이 뱅크에 표시된
  급수 수준으로 "자연스럽게" 읽히는지는 검증하지 않는다 (그래서 레벨 표기 자체를 없앴다).

## 확장 원칙

표현을 추가할 때는 다음을 지킨다.

1. 단어가 아니라 구조(접속 형태가 있는 것)여야 한다
2. 실제로 지문에 넣어보고 자연스럽게 나오는지 확인한 것만 추가한다
3. 외부 사이트 목록을 그대로 복사하지 않는다 — 저작권 문제
4. `grammar_bank.py`의 해당 카테고리 `_bank(...)` 호출에 문자열만 추가하면 된다.
   `〜`로 접속 형태를, `/`로 대체 표현을, `(...)`로 구분용 설명을 표시하는 규칙을 따르면
   파서가 자동으로 검증용 패턴을 만든다.
5. 결합 범위가 좁거나 뒷문장과 짝을 이뤄야 하는 표현이면, 문자열 대신
   `("표현", "사용지침")` 튜플로 등록하고, 구조적으로 검증 가능하다면
   `get_grammar.py`의 `_EXTRA_CHECKS`에 검증 함수를 추가한다.
