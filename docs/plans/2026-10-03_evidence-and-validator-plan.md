## 2. 우선순위 재편 (효과 큰 순)
**P0 — 측정 인프라 (저위험, 코드 변경 승인 필요)**
- 시도마다 `{판정 상태(실행/호출실패/파싱누락), 판정 이유(note), 응답 모델}`을 기록. 판정 NG 이유가 메일에만 있는 문제와 가동률 미기록 해소. 기존 `UsageRepository`(D1)의 최소판으로 먼저 도입.
**P1 — 결정적 검증기 수정 (가장 확실한 개선, 승인 필요)**
- (a) **활용형·변형 허용**: 문형별 허용 정규식(예: `を禁じ得(ない|なかった|なく…)`, `なり(に|の)`, `(と|が)相まって`, `に(伴|ともな)って`). 시제품 정상 14/14 인식, 오탐 8개 중 1개(현행 문자열 매칭과 같은 수준).
- (b) **어휘 목록 방식 재설계**: 목록 협소로 오탈락(あげく 「断られた」, ばかりに 「大損・事故・試験に落ちた」, を禁じ得ない 「疑問・同情」, にかたくない 「予想」, くせに 비판어 없는 자연문, いかんによって 「変更」). 목록을 넓히는 것만으로는 오통과(あげく 뒤 「結局、見事に成功」)가 남으므로, **목록 밖은 "미판정"으로 두고 LLM 판정·증거 단계로 넘기는 3상태(통과/실격/미판정)**를 검토.
- (c) **영구 회귀 세트**: 이번에 만든 "자연문(통과해야 함)/비문(실격이어야 함)" 배터리를 `tests/`에 상시 테스트로 추가 — **양방향(오탈락·오통과) 측정**. 기존 테스트는 양성 사례 위주였음. 시드 고정 분포 테스트 교훈 동일 적용.
- (d) 보관된 실패 지문·shadow snippet으로 현행/개정 규칙 리플레이 diff.
**P2 — 웹 증거 검증 (역할 축소·shadow 우선)**
- 모델: **2.5-flash**(현 키에서 유일하게 동작) 또는 결제 변경 후 3.5 — §7 결정.

- **번복 enforce는 보류**: 사용자 결정("웹이 자연스럽다고 하면 통과")은 유지하되, 실측상 증거 신뢰도가 낮아 **shadow→기록만**을 기본으로 하고 전환 기준(§5)을 충족하기 전엔 켜지 않음. P1이 오탈락의 근본 원인을 먼저 제거하므로 번복 필요량 자체가 줄어든다.
**P3 — 용법 저장소 전체(D1 확장)·월간 통합 리포트·생성 반영**: 기존 설계 2·3·4 유지, 단 아래 §4 수정.

## 3. 설계 1·5 수정 (증거 검증과 기존 규칙 검증)
- 증거 검증 흐름·조정표는 유지하되 **증거 verdict의 신뢰 가정을 낮춘다**: `valid/invalid/insufficient` 외에 **`inconsistent`(2회 불일치)**를 추가하고 `inconsistent`는 `insufficient`와 동일 취급.
- 코드 실격에 대한 웹 번복: 결정은 유지하나 **P1 이후 남는 오탈락에 한정**하고 shadow로 먼저 측정. 번복 건은 규칙 개정 후보로도 누적.
- **설계 5(기존 규칙 검증) 방법 변경**: 규칙 주장의 웹 검증은 도구 한계로 **보조 수단**으로 격하. 주 수단은 ①배터리 시험(P1c) ②실제 실패 로그 리플레이 ③사용자 확인. 아래 규칙 중 배터리로 **오탈락이 확인된 것**: を禁じ得ない(앞 어휘 6개·과거형)/にかたくない(앞 어휘 4개)/あげく·ばかりに(결과어 목록)/くせに(비판어 창)/いかんによって(「変更」)/활용형 13개 문형(を禁じ得ない・てやまない・にほかならない・にかたくない・にたえない・に違いない・まんざら〜でもない・あながち〜とは言えない・きらいがある・に決まっている・なんとか〜ようにする・らしい(과거)・っぽい(과거)).
- **문형 은행 변형 정의**: `なりに`↔`なりの`, `と相まって`↔`とが相まって`, `に伴って`↔`にともなって`, `たとえ〜としても`↔`たとえ〜ても` 등은 **같은 문법 항목인지 사용자·자료로 확정**한 뒤 은행에 변형으로 등록(Gemini 탓으로 돌린 실패 중 일부가 사실은 정의 문제일 수 있음).
- **생성 측 개선 후보(별개)**: 짧은 조사류(さえ・こそ・すら・までも…) 통째 누락이 실패의 큰 몫 — 이미 위험군 상한(캡) 적용. 추가 후보는 누락 시 **재시도 피드백에 "빠진 문형을 보강하는 수정 지시"**, 한 번에 5개를 모두 쓰게 하는 부담 완화 등(실험 필요, 별도 승인).

## 4. 설계 2·3·4 수정 (저장소·생성 반영·리포트)
- 저장소 최소 필드를 P0에서 먼저: 판정 상태·판정 이유·응답 모델·`rules_version`·`evidence_mode`.
- `judge_ng→web_ok` 사례의 **`confirmed` 승격 조건 변경**: "적격 출처 ≥2"는 비현실적 → **사람(월간 메일 검토)이 확인**한 건만 `confirmed`. 자동 승격 없음. 생성 반영(설계 3)은 사람 확인된 사례만 사용(오류 되먹임 방지 강화).
- 월간 리포트 섹션 추가: **판정 가동률**, **증거 호출 성공률·적격 출처 비율·판정 일관성**, 규칙 개정 후보, 오탈락/오통과 배터리 결과(수동 갱신), 번복 건(있다면) 전수.
