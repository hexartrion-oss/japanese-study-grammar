# japanese-study-grammar

일본어 **문법 구조** 학습 메일링. [japanese-study](https://github.com/hexartrion-oss/japanese-study)의
자연스러운 지문 생성 파이프라인을 그대로 가져와, 학습 대상을 문법으로 좁힌 자매 리포지토리다.

> 이 리포는 한 차례 전면 개편을 거쳤다. 최초 버전은 동사 활용표를 만드는 방식이었지만,
> "사전만 찾으면 풀리는 것"이라는 문제 제기 이후 방향을 완전히 바꿨다. 지금 이 문서는
> 그 개편 이후의 최종 방침만 담고 있다.

## 핵심 원칙

**1. 힌트를 주지 않는다.**
지문에 강조 표시, 문법 설명, 한국어 번역을 일절 넣지 않는다. 학습자가 지문을 읽고 스스로
번역하면서 "이 표현이 왜 여기 있는지"를 알아채는 방식이다. 정답을 주면 그 순간 암기 문제가
되어버린다.

**2. 문법 카테고리를 숨긴다.**
메일 제목에도, 본문 어디에도 오늘이 무슨 카테고리인지 드러나지 않는다. 카테고리 정보는
운영자용 `run_log.txt`에만 남는다. 사용자가 보는 건 순수한 읽을거리 한 편뿐이다.

**3. 문법은 단어가 아니라 구조로만 다룬다.**
부사 하나(せっかく)를 그냥 던져놓지 않는다. 반드시 문형 세트(せっかく〜のに)로 등록한다.
빼면 문장이 안 되는 것, 접속 형태가 있는 것만 문법으로 취급한다.

**4. 문형 뱅크는 스크래핑하지 않는다.**
JLPT 학습 사이트들의 문형 목록은 그 자체가 저작물이다. 개수·분류 체계 같은 규모 감각만
참고하고, 실제 항목은 하나하나 직접 검증해서 채운다. 그래서 카테고리별 개수가 균일하지
않고, 운영하면서 실제 지문에 넣어본 것만 점진적으로 늘어난다.

**5. 같은 문형이 너무 자주 반복되지 않게 한다.**
쿨다운 로직으로 최근 사용 이력을 추적한다. 아래에서 자세히 설명한다.

## 요일별 카테고리

| 요일 | 카테고리 키 | 레벨 | 보유 문형 수 |
|---|---|---|---|
| 월 | `adverb` (부사+구문 세트) | N3+ | 18 |
| 화 | `quotation` (인용·전문·양태) | N3+ | 17 |
| 수 | `emphasis` (강조 조사·역접 접속) | N3~N2 | 16 |
| 목 | `business` (비즈니스·뉴스체 논리 접속) | N2+ | 19 |
| 금 | `literary` (N1 문어체 전용) | N1 | 21 |

주말은 순환표에 없고, 스크립트가 실행되면 자동으로 월요일 카테고리로 대체된다.

문형 목록 실물은 `grammar_bank.py`에 있다. 예시(부사 카테고리 일부):
`せっかく〜のに · どうせ〜なら · たとえ〜としても · むしろ〜べきだ · いっそ〜ばよかった`

## 문서 템플릿

원본 japanese-study와 같은 형식이다. 차이는 소스 URL 줄이 없다는 것뿐이다(지어낸 이야기라
출처가 없다).

```
日本語学習 読み物
2026-09-07 (Mon) | Week 37
[ N3+ ]
テーマ: 転職を迷う友人の話

（10〜15문장 순수 일본어 지문 — 강조·설명·번역 전혀 없음）
```

메일 제목도 카테고리를 노출하지 않는 중립적인 형태다: `日本語学習 読み物 · 2026-09-07 (Mon)`

## 쿨다운 로직

1. 매일 실행 시 오늘 카테고리에서 **최근 3회** 안에 쓰인 문형을 이력 파일에서 확인한다
2. 그 문형들을 제외한 후보 중에서 5개를 무작위로 뽑는다
3. Gemini로 지문을 생성하고, 5개가 실제로 자연스럽게 들어갔는지 검증한다
4. 검증에 실패하면 재시도한다 (2회 실패 시 문형 조합 자체를 교체)
5. 검증을 통과해 **메일 발송에 성공한 경우에만** 이력을 갱신하고 리포지토리에 자동 커밋한다

발송이 실패하면 이력을 건드리지 않는다 — 안 보낸 문형을 "사용됨"으로 잘못 기록하는 걸
막기 위해서다.

카테고리당 16~21개 보유 중이라, 최근 3회를 제외해도 후보가 충분히 남는다. 조합 수 기준으로
1년(52주) 순환에는 여유가 크다. 다만 개별 문형 하나는 카테고리 내에서 평균 3~4주마다
재등장하는데, 이는 의도된 설계다 — 너무 길지도 짧지도 않은 간격 반복이 오히려 기억에 도움이
된다.

이력은 `used_history.json`에 저장되고, GitHub Actions 실행 환경에서는 워크플로가 발송 성공
시 이 파일을 자동으로 커밋·푸시한다. GitHub Actions는 매번 새 가상머신에서 시작하기 때문에,
이 자동 커밋이 없으면 다음 실행이 이전 이력을 전혀 알 수 없다.

## 파일 구성

```
grammar_bank.py   문형 뱅크 (요일별 카테고리, 문형 검증용 파서 포함)
get_grammar.py    카테고리 선정 → 쿨다운 필터링 → 지문 생성 → 검증 → 발송 → 이력 커밋
```

## 설정

리포지토리 Secrets에 다음 4개를 등록한다.

| 이름 | 설명 |
|---|---|
| `GMAIL_ADDRESS` | 발신 Gmail 주소 |
| `GMAIL_APP_PASSWORD` | 2단계 인증 후 발급한 앱 비밀번호 16자리 |
| `EMAIL_RECIPIENTS` | 수신자, 쉼표로 구분 |
| `GEMINI_API_KEY` | Google AI Studio 발급 키 |

로컬 실행은 `.env.example`을 `.env`로 복사해 채운다.

```bash
pip install -r requirements.txt
python get_grammar.py
```

특정 카테고리만 확인하려면:

```bash
FORCE_CATEGORY=literary python get_grammar.py
```

Actions에서는 **Run workflow**로 카테고리와 수신자를 지정해 수동 실행할 수 있다. `mail_to`를
채우면 그 주소로만 발송돼서, 다른 구독자에게 테스트 메일이 가는 걸 막을 수 있다.

로컬 실행에서는 이력 파일이 로컬에만 저장되고 git 커밋은 되지 않는다(`GITHUB_ACTIONS` 환경
변수가 있을 때만 커밋을 시도한다).

## 폰트

지문에 일본어만 들어가므로 일본어 전용 폰트로 충분하다. 워크플로는 `fonts-noto-cjk`를
설치한다. 직접 지정하려면 `JAPANESE_FONT_PATH`를 쓴다.

## 검증 로직의 한계

- 문형이 실제로 지문에 들어갔는지는 부분 문자열 매칭으로 확인한다. 완전한 문법 파싱이
  아니라서, 우연히 같은 글자가 다른 의미로 등장해도 통과 처리될 수 있다 (예: "上で"는
  문형이지만 일반적인 "~위에서"라는 뜻으로 쓰여도 매칭된다).
- Gemini가 한자로 표기하는 흔한 경우(예: `ば良かった` vs `ばよかった`)는 정규화 테이블로
  보정하지만, 모든 한자/히라가나 변형을 다 커버하지는 못한다.
- `そうだ(伝聞)`와 `そうだ(様態)`는 문자열만으로는 구분이 안 돼서, 둘 다 `そうだ`라는
  글자만 확인한다. 실제로 어느 쪽으로 쓰였는지는 검증하지 못한다.

## 확장 원칙

문형을 추가할 때는 다음을 지킨다.

1. 단어가 아니라 구조(접속 형태가 있는 것)여야 한다
2. 실제로 지문에 넣어보고 자연스럽게 나오는지 확인한 것만 추가한다
3. 외부 사이트 목록을 그대로 복사하지 않는다 — 저작권 문제
4. `grammar_bank.py`의 해당 카테고리 `_bank(...)` 호출에 문자열만 추가하면 된다.
   `〜`로 접속 형태를, `/`로 대체 표현을, `(...)`로 구분용 설명을 표시하는 규칙을 따르면
   파서가 자동으로 검증용 패턴을 만든다.
